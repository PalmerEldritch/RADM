## Production-path physical smoke

### Start without an established fix, then acquire

- Precise location permission and system location services were available.
- Running was started through the production UI and location-type foreground service.
- The session immediately showed `RECORDING`; active time reached 14 seconds while
  the UI still showed `Acquiring location` and no distance.
- The first accepted real GPS sample was retained at active elapsed 27,349 ms.
- The same activity UUID remained authoritative and the UI transitioned to
  `Location available` without restart.
- The recording finished with 181 accepted positions durably present in Room.
- Retained horizontal accuracy ranged from approximately 0.51 m to 12.25 m.

Result: PASS (`VVM-REC-003`, `VVM-REC-004`).

### Live distance and retained source data

- Real, non-mock accepted GPS displacement increased the production UI from no
  distance to `0.02 km`.
- Recalculation from the retained coordinates using the specified per-segment
  haversine semantics produced 20.215 m.
- Every inspected retained position included its activity identity, accepted-only
  sample index, route segment, UTC timestamp, active elapsed time, coordinates,
  and horizontal accuracy.

Result: PASS for the M5 provisional live-distance and accepted-position persistence scope.

### Temporary location loss and recovery

- After real acquisition was established, Android location services were disabled
  for a controlled interval and then restored.
- The existing location foreground service remained active with the same activity
  UUID while location was unavailable.
- No accepted position exists between elapsed 78,349 ms and 132,349 ms.
- Acquisition resumed automatically after location services were restored.
- The resumed accepted data began a later route segment; no activity restart was
  required.
- Retained data contained segments 0, 1, and 2. The production distance calculation
  included 20.215 m within segments and excluded 0.514 m across segment boundaries.
- Active elapsed time reached 283,691 ms and the recording remained finalizable.

Result: PASS (`VVM-LOC-006`, `VVM-LOC-008`, `VVM-REL-004` and the device portion of
the M5 exit criterion). This is an M5 smoke test, not completion of the longer
`VVM-FIELD-004` campaign assigned to M14.

### Approximate/coarse-only capability

- Fine location was revoked while coarse location remained granted.
- RADM identified `Approximate location only` before Start.
- The Android precise-location upgrade prompt was declined by retaining approximate
  location.
- The location-type foreground service started successfully and active time advanced.
- The live state progressed from `Acquiring location (approximate only)` to
  `Location unavailable (approximate only)` after 15 seconds without an accepted fix.
- Zero position rows were retained and no distance was shown.

Result: PASS for the approximate-location branch of `VVM-PERM-001`.

### Missing foreground-service prerequisites before Start

Two user-visible Start attempts were exercised separately:

1. System location services disabled with location permission granted.
2. Both fine and coarse location permission denied through the Android permission prompt.

For each attempt:

- RADM identified the blocking capability;
- no foreground recording service was started;
- no unresolved recording session was created;
- the UI did not represent the activity as recording.

Result: PASS for `SRS-LOCSTART-001`, `RECM-FGS-004`, and the no-location-permission
branch of `VVM-PERM-001` under the revised location-FGS architecture.
